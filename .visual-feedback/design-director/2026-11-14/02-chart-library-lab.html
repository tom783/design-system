Round 03 · 차트 라이브러리 결정

차트는 위젯이 아니라
디자인 시스템의 구성요소다

후보 7종의 라이선스·버전·유지 상태를 npm 원본에서 확인했고, 그중 둘은 걸러졌습니다. 남은 선택의 핵심은 기능표가 아니라 우리 토큰을 차트가 상속할 수 있는지입니다. 그건 글로 읽어서는 판단이 안 되니, 아래 01에서 테마를 직접 바꿔 보시면 됩니다.

테마
브랜드

테마·브랜드를 바꿀 때 어느 차트가 따라오는지 보세요

01

결정의 핵심 — 차트가 토큰을 상속하는가

우리 디자인 시스템은 색을 CSS 변수로 관리합니다. 라이트/다크 전환도, 브랜드 컬러 교체도 변수 값만 바뀝니다. SVG 는 fill="var(--brand-600)" 로 그 변수를 직접 받습니다. Canvas 는 받지 못합니다 — 픽셀을 찍는 시점의 색을 JS 가 알아야 합니다.

SVG · visx / Recharts 계열 var(--token) 직접 참조
따라옴 테마·브랜드를 바꾸면 JS 한 줄 없이 즉시 반영됩니다. 차트가 버튼·테이블과 같은 색 체계 안에 있습니다.
Canvas · ECharts / Chart.js 계열 JS 가 색을 넘겨줘야 함
안 따라옴 픽셀이 이미 찍혔습니다. 테마를 바꿔도 그대로입니다.
재렌더 0회
공정하게 말하면 Canvas 도 따라올 수 있습니다. 다만 그 배선을 우리가 영구히 소유해야 합니다

위 "다시 그리기" 버튼이 하는 일이 그것입니다 — getComputedStyle 로 변수 값을 읽어 차트 설정 객체에 주입하고 재렌더합니다. 문제는 이게 한 번이 아니라 모든 테마 변경 지점에 훅으로 걸려 있어야 한다는 것입니다. OS 테마 변경(prefers-color-scheme 미디어쿼리 리스너), 사용자 토글, 브랜드 교체, 그리고 차트가 여러 개면 전부. 빠뜨린 한 곳이 "다크모드에서 차트만 밝은" 버그가 됩니다. SVG 쪽에서는 이 코드가 아예 존재하지 않습니다.

03

visx 로 무엇을 얻는가 — 복합 인코딩 5종

"단순 바·라인 말고 정보 전달에 효과적인 복합적인 방법"이라는 요구가 실제로 무엇인지 우리 커머스 데이터로 그렸습니다. 아래 다섯은 모두 기성 차트 컴포넌트로는 만들기 어렵거나 불가능한 것들입니다. 전부 손으로 쓴 SVG 이고, visx 를 쓰면 스케일·축 계산만 라이브러리가 대신합니다.

04

비용 — 같은 차트, 두 접근

visx 는 공짜가 아닙니다. 같은 영역 차트를 만드는 데 드는 코드량 차이가 이 결정의 대가입니다. 기본 차트에서는 Recharts 가 3배 짧고, 복합 차트에서는 역전됩니다.

Recharts — 기본 영역 차트12줄
// 선언형. 축·격자·툴팁이 기본 제공된다.
<AreaChart data={daily} width={560} height={200}>
  <CartesianGrid stroke="var(--grid)" />
  <XAxis dataKey="date" />
  <YAxis />
  <Tooltip />
  <Area
    type="monotone" dataKey="orders"
    stroke="var(--brand-600)"
    fill="var(--brand-200)"
  />
</AreaChart>
빠름 여기까지는 Recharts 가 분명히 유리합니다.
visx — 같은 영역 차트약 35줄
// 프리미티브. 스케일을 직접 만들고 축을 배치한다.
// 그 대가로 모든 좌표가 우리 통제 아래 있다.
const x = scaleTime({
  domain: [min(dates), max(dates)],
  range: [48, width - 12],
});
const y = scaleLinear({
  domain: [0, max(orders) * 1.1],
  range: [height - 28, 12], nice: true,
});

<svg width={width} height={height}>
  <GridRows scale={y} width={width}
    stroke="var(--grid)" />
  <AreaClosed data={daily} yScale={y}
    x={d => x(d.date)} y={d => y(d.orders)}
    fill="var(--brand-200)"
    curve={curveMonotoneX} />
  <LinePath data={daily}
    x={d => x(d.date)} y={d => y(d.orders)}
    stroke="var(--brand-600)" strokeWidth={1.8} />
  <AxisBottom scale={x} top={height - 28} />
  <AxisLeft scale={y} left={48} />
</svg>
느림, 그러나 03의 다섯 가지는 이 방식에서만 나옵니다.
비용을 한 번만 치르는 구조 우리가 만드는 것은 차트가 아니라 차트 컴포넌트 세트입니다

35줄은 차트 종류당 한 번 드는 비용입니다. <TrendArea>, <BulletRow>, <CompositionBand> 처럼 토큰이 박힌 컴포넌트로 포장해 두면, 실제 화면에서 쓰는 코드는 <TrendArea data={daily} /> 한 줄입니다. Recharts 로 가면 매 화면에서 12줄을 반복하거나, 똑같이 래핑해야 합니다 — 래핑은 어차피 해야 하므로, 래핑 안쪽이 프리미티브인지 기성 차트인지가 진짜 선택입니다. 안쪽이 기성 차트면 그 차트가 허용하는 것까지만 할 수 있습니다.

05

권고와 결정 요청

권고 visx 채택 + ECharts 를 좁은 탈출구로 남긴다

visx 로 우리 차트 컴포넌트 세트를 만들어 디자인 시스템에 넣습니다. 토큰을 그대로 상속하고, 복합 인코딩이 가능하고, visx 가 멈춰도 잃는 게 적습니다.

단 하나 visx 가 약한 영역이 있습니다 — 10만 포인트 이상을 실시간으로 그리는 화면입니다. SVG 는 포인트마다 DOM 노드를 만들기 때문에 수만 개에서 느려집니다. 그런 화면이 생기면 ECharts 를 그 화면에만 쓰고, 토큰을 JS 로 주입하는 배선을 한 곳에만 만듭니다. 지금 당장 그런 화면은 없으니 도입하지 않고, 필요해질 때까지 미룹니다.

확인 방법

01의 두 차트는 같은 데이터·같은 모양입니다. 상단 바에서 테마를 바꾸면 왼쪽(SVG)만 따라오고, 브랜드를 청록으로 교체해도 왼쪽만 바뀝니다. 오른쪽(Canvas)은 "다시 그리기"를 눌러야 따라옵니다 — 그 버튼이 곧 우리가 영구히 유지해야 할 코드입니다.

라이선스·버전·배포일은 2026-11-14 npm 레지스트리 직접 조회값입니다. 03의 차트는 전부 손으로 쓴 인라인 SVG 이며, 색은 R01 에서 확정한 프로젝트 토큰을 씁니다. 페이지 UI 자체는 차트 판단을 오염시키지 않도록 무채색으로 고정했습니다.
